## 1. Database Schema & Storage (D1 SQLite)

### Specification (`docs/DATABASE.md`, `migrations/`)
- Column type: `DATETIME DEFAULT CURRENT_TIMESTAMP` for timestamps (`created_at`, `updated_at`, `downloaded_at`, `redeemed_at`, `last_sign_in_at`).
- Column type: `DATETIME NOT NULL` or `DATETIME` for expirations (`expires_at`, `starts_at`, `tier_expires_at`, `current_period_end`).
- Column type: `TEXT` for day-level and month-level tracking counters (`last_download_date`, `month_cycle_start`).

### Reality in Source Code
- **SQLite Default Format**: `YYYY-MM-DD HH:MM:SS` (generated by SQLite `CURRENT_TIMESTAMP`, e.g. `2026-11-04 11:49:54`).
- **Programmatic Inserts / Updates**: When JS writes to D1 via `/api/data` or functions, it frequently passes ISO-8601 strings: `new Date().toISOString()` -> `YYYY-MM-DDTHH:mm:ss.sssZ` (e.g. `2026-11-04T11:49:54.123Z`).
- **Quota Date Columns**:
  - `last_download_date`: Stored strictly as `YYYY-MM-DD` (e.g. `2026-11-04`).
  - `month_cycle_start`: Stored strictly as `YYYY-MM` (e.g. `2026-11`).

### Drift Detected
- **Mixed Timestamp Formats in D1 Tables**:
  - SQLite default values store space-separated UTC timestamps without timezone offset: `2026-11-04 11:49:54`.
  - JS updates in functions and frontend store ISO-8601 strings with `T` and `Z`: `2026-11-04T11:49:54.123Z`.
  - *Impact*: In JS, `new Date(str)` handles both formats transparently. In SQLite SQL queries comparing dates as strings (`starts_at <= datetime('now')`), string sorting can fail if formats diverge.
  - *Fix Applied in Promotions*: In `AdminCampaignManager.tsx`, the start and expiration dates are explicitly converted to SQLite format: `new Date(startsAt).toISOString().replace("T", " ").slice(0, 19)`.

## 2. Serverless API Endpoints (`functions/api/`)

### Specification & Patterns
- Timestamps in JSON responses and internal token records (`auth`, `sessions`, `download`, `entitlement`, `orders`).

### Reality in Source Code
- **Full ISO-8601 UTC String**:
  - Format: `YYYY-MM-DDTHH:mm:ss.sssZ` via `new Date().toISOString()`.
  - Used in:
    - Session expiration: `new Date(Date.now() + 7 * 24 * 60 * 60 * 1000).toISOString()`
    - Account verification / OTP validity: `new Date(Date.now() + 60 * 60 * 1000).toISOString()`
    - Order purchase timestamps: `purchased_at: new Date().toISOString()`
    - Security audit logs: `timestamp: new Date().toISOString()`
- **Date Slicing for Daily Windows**:
  - Format: `YYYY-MM-DD` via `new Date().toISOString().slice(0, 10)` or `.split("T")[0]`.
  - Used in:
    - Daily email rate limiter (`functions/api/send-email.ts`)
    - Daily download quota checking (`functions/api/entitlement.ts`)
- **Email Receipt Date Formatting**:
  - Format: `new Date(periodEnd).toLocaleDateString("en-US", { year: "numeric", month: "long", day: "numeric" })` -> e.g., `"November 4, 2026"` (`functions/api/subscribe-pro.ts`).

### Drift Detected
- No logical drift in API calculations. All time comparisons convert string inputs into `new Date(str).getTime()` before comparing with `Date.now()`.

## 4. Frontend UI Display Formats

### Reality in Source Code
Across UI components, four different display strategies are currently in use:

1. **System Locale Default (`toLocaleDateString()`)**:
   - Code: `new Date(item.created_at).toLocaleDateString()`
   - Used in: `AdminInquiries.tsx`, `AdminOrders.tsx`, `DashboardCustomTab.tsx`, `StorageBucketExplorer.tsx`, `SubscriptionsTable.tsx`, `ClientAccountsTable.tsx`, `AdminCampaignManager.tsx`.
   - Result: Format varies depending on client browser (e.g., `11/4/2026` in US vs `04/11/2026` in India/UK).

2. **Explicit Standardized US Locale (`toLocaleDateString("en-US", ...)`)**:
   - Code: `d.toLocaleDateString("en-US", { day: "numeric", month: "short", year: "numeric" })`
   - Used in: `AdminTemplates.tsx`, `RevokeProModal.tsx`, `subscriptionEmails.ts`.
   - Result: Uniformly renders e.g., `"Nov 4, 2026"` or `"4 Nov 2026"`.

3. **Locale Date & Time (`toLocaleString()`)**:
   - Code: `new Date(inquiry.createdAt).toLocaleString()`
   - Used in: `InquiryDetailModal.tsx`.
   - Result: e.g. `"11/4/2026, 5:19:32 PM"`.

4. **Time Only (`toLocaleTimeString(...)`)**:
   - Code: `new Date().toLocaleTimeString([], { hour: "2-digit", minute: "2-digit", second: "2-digit" })`
   - Used in: `Admin.tsx` header status, `TemplatesTableView.tsx`.
   - Result: e.g. `"05:19:32 PM"`.

5. **Editorial Month & Year (Marketing & Blog Content)**:
   - Format: `"Month YYYY"` string (e.g. `"September 2026"`, `"October 2026"`).
   - Used in: `src/features/blog/defaultArticles.ts`, `src/pages/Blog.tsx`, `src/pages/BlogDetail.tsx`.
   - Schema JSON-LD: `datePublished: "2026-09-01T00:00:00Z"`.

6. **Relative Remaining Time Calculation**:
   - Format: `Math.ceil((new Date(expiry).getTime() - Date.now()) / (1000 * 60 * 60 * 24))` -> e.g. `"28 Days Left"`.
   - Used in: `SubscriptionsTable.tsx`, `useClientLedger.ts`, `useAuthPage.ts`.

7. **Copyright Year**:
   - Code: `new Date().getFullYear()` -> `"2026"`.
   - Used in: `Footer.tsx`.

## 5. Summary & Drift Action Items

1. **Storage Discrepancy**:
   - Cloudflare D1 auto-generated timestamps use SQLite format: `YYYY-MM-DD HH:MM:SS`.
   - API / Client programmatically generated timestamps use ISO-8601: `YYYY-MM-DDTHH:mm:ss.sssZ`.
   - *Recommendation*: When querying D1 using date filters (`WHERE created_at > ?`), wrap comparison columns in SQLite's `datetime(?)` function or pass `YYYY-MM-DD HH:MM:SS` (as done in `AdminCampaignManager.tsx`).

2. **UI Display Discrepancy**:
   - Some tables use browser-dependent `toLocaleDateString()`, causing dates to look like `11/4/2026` for some users and `04/11/2026` for others.
   - Other tables use explicit options `{ month: "short", day: "numeric", year: "numeric" }` yielding `"Nov 4, 2026"`.
   - *Recommendation*: Standardize all client-facing UI dates on a shared helper `formatDate(dateStr)` that outputs the brand standard `"Nov 4, 2026"` (or `"04 Nov 2026"`).
